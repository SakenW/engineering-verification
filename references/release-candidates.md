# 候选冻结与昂贵门禁

- 区分交付范围与验证深度；`full`、`all` 或 `production` 不自动授权执行昂贵的全仓验证。
- 昂贵门禁前先完成廉价静态检查，以及只读的环境、凭据存在性、runner、网络、registry 和容量预检，并明确被验收的候选提交或制品集。
- 完整门禁只用于已完成聚焦修复和局部验证的冻结候选。门禁失败后先单独复现失败切片、批量修复同类问题，候选重新稳定前不得反复重跑完整门禁。
- SSH、runner、生产配置、registry 或镜像传输失败属于发布通道问题，不自动推翻仍适用于同一不可变候选的代码证据；不得为重试未变化的通道问题制造无意义的新提交或制品。
- 不得为同一候选启动重复或并发的昂贵运行；正在取得可验证进展的操作只能因安全、正确性、候选过期或用户明确决定而停止。
- 对已签名候选的容量、SSH、runner、registry 或制品物化失败，先做一次最小只读诊断，并只提取第一个可操作根因。候选提交、签名身份、制品哈希和影响范围未变时，禁止重新触发完整候选构建、重签、重放完整日志或重复完整门禁；先复用原候选，仅在重新核对相应前置条件已变化后，才可重跑失败的部署步骤。只有候选/制品身份失效、候选字节变化，或失败证据明确指向构建阶段时，才允许重新构建。
- 诊断日志默认先读取失败 job/步骤的状态、时间和退出码，再以已知错误词或时间窗定向提取首个根因及其必要上下文；禁止直接把完整 CI、SSH、容器或服务日志流入对话。只有首个根因不足以决定下一步时，才可逐段扩大范围，并说明新增读取要验证的具体假设；完整日志须落到本地产物并按行号引用，不能作为常规对话输出。
- 长任务采用粗粒度监控，仅在状态变化、阻塞或完成时汇报；重复且无变化的轮询输出不构成进度证据。
